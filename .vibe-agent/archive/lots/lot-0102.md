## Objectif

Deuxième lot de l'epic « US & Jira » : le backlog peut porter un pointeur Jira vérifié en
format (`integrations.jira.key`), sans jamais synchroniser ni dupliquer de contenu Jira —
même philosophie que le pointeur `us` (lot #101).

## Décisions (et pourquoi)

- Sous-champ `integrations.jira` (pas un champ top-level) : réutilise le namespace déjà
  existant pour la métrologie RTK plutôt que d'en créer un second, cohérent avec le
  commentaire d'en-tête mis à jour (« pas de champs Jira » était obsolète, épic l'a dépassé).
- Validation FORMAT uniquement (`JIRA_KEY_RE`, `PROJ-123`), jamais d'existence réseau : un
  identifiant Jira ne se vérifie pas comme un chemin de fichier (pas d'accès API prévu ici).
- `jira --id N [--set KEY]` reproduit exactement le patron `verify --id N [--set …]` déjà en
  place — lecture sans `--set`, correction après coup avec, aucune nouvelle convention CLI.
- Piège RTK corrigé dans la même passe : `startLot`/`doneLot` réécrivaient tout
  `lot.integrations` (pose/retrait de `command_optimizer`) — un `integrations.jira` déjà posé
  aurait été détruit en silence au premier (re)démarrage ou à la clôture. Les deux préservent
  désormais le sous-champ de l'autre.
- Réouverture du lot #102 tracée (`reopen --note`) avant tout code : la clôture staged trouvée
  au démarrage de la session (status done, closed_verify=timeout, closed_commit pointant vers
  le commit de clôture du lot #101, aucun code jira écrit) violait « fait = prouvé ».
