# Lot #97 — Série fiable : depends_on dans nextLot + gates de vague

- epic : Archive à tiroirs · clos : 2026-07-27 · commit : 3cf81f0 · session : inconnue
- verify : `node test/run-tests.js` → OK (1508) · coût : non mesuré

## Objectif

Fermer les trois derniers trous de fiabilité du canal série/vague relevés au catalogue
(mwn/promptimizer-archive-handoffs/02 : FIA-18, FIA-16, FIA-17) : depends_on n'était exploité que
par le parallèle (nextLot renvoyait le premier todo du tableau, l'auto-clôture propageait la
proposition aveugle) ; un lot sans verify était mergé sans filet (coupable faux en cascade) ;
« vague close » se déduisait des seuls statuts, sans vérifier l'état fusionné.

## Décisions (et pourquoi)

- Forme de retour de nextLot INCHANGÉE (lot nu) + helper séparé blockedByOf(b, lot) plutôt qu'un
  objet enveloppe : 8 consommateurs, dont statusline qui tourne à chaque refresh et ne doit jamais
  throw — changer le contrat pour un marqueur d'affichage aurait été un coût de régression inutile.
- Marqueur JAMAIS persisté : on n'annote pas l'objet lot (un saveBacklog ultérieur l'écrirait dans
  backlog.json, et normalizeLots le dropperait ensuite). Calculé à la volée, pur, zéro E/S.
- Sémantique des dépendances alignée sur planWaves : une dep ne bloque que si elle pointe un lot
  PRÉSENT au statut todo/in_progress ; done, dropped ou id inconnu = satisfaite. Sans cette
  tolérance, un depends_on vers un lot abandonné gèlerait le plan pour toujours.
- Repli anti-régression : sur cycle, nextLot renvoie quand même le premier todo + son marqueur.
  Jamais null tant qu'il reste des todo, sinon lotClosedMessage annoncerait « Plan de lots terminé »
  à tort.
- Refus « no-gate » placé AVANT le checkout, pas dans la boucle : la commande est délibérée (elle
  PEUT refuser, contrairement aux hooks), et un refus tardif aurait laissé des merges à moitié
  faits. Sortie --json structurée (reason:'no-gate'), cohérente avec no-integration-branch.
- Cran (2) de FIA-16 implémenté en flag CLI --gate <cmd> et non en champ persisté dans fleet.json :
  aucun changement de schéma, testable via l'injection opts.verify existante.
- Union du gate final bâtie sur TOUS les lots du fleet, pas sur plan.steps : planReintegration
  exclut les lots déjà reintegrated, donc en pipeline multi-runs l'union du dernier run raterait
  les verify des runs précédents.
- Déduplication d'exécution : on retire de l'union la dernière commande déjà passée verte sur
  l'état final (un verify coûte jusqu'à 600 s). Un --final-gate explicite tourne toujours.
- Gate final rouge : PAS de rollback, PAS de retouche des états fleet reintegrated — les merges
  restent faits, seul le signal de clôture est retenu (D3 palier 2 : l'humain arbitre).
- Cas dégénéré (aucun verify dans la vague) : on CLÔT en le disant (finalGate.reason='no-gate')
  plutôt que de bloquer — cohérent avec l'esprit prudent-mais-non-mutique de la commande.
- Effet de bord assumé : aggregateChangelog ne revendique plus « gate verify vert » pour un lot
  mergé sous --allow-no-gate (c'était une affirmation fausse pour TOUS les lots sans gate).

## Vérifié

- 1508 tests OK (+55) : sémantique des dépendances (done/dropped/inconnu/in_progress), ordre du
  tableau inversé, cycle, non-persistance du marqueur, les 3 surfaces d'annonce, CLI next/about,
  refus no-gate (texte + --json, zéro merge tenté, fleet intact), --gate de repli, gate final rouge
  (2 merges conservés, états fleet intacts, aucune vigie émise), already-green (1 seul appel
  verify), union non limitée au dernier step (ordre A|B|A).
- Non-persistance vérifiée aussi sur le backlog RÉEL du dépôt : 0 clé "blockedBy" dans
  .vibe-agent/backlog.json après plusieurs appels nextLot / next / statusline.
- Canal plugin : build-plugin.js repasse (artefact dérivé, rien à éditer côté plugin).

## Non vérifié

- Le pipeline de réintégration sur une VRAIE vague multi-sessions : jamais exécuté hors bac à
  sable (les tests font du git réel, mais en sandbox et avec des gates `true`/`false`).
- Le gate final avec une commande longue réelle (typecheck+tests+build) : seuls des stubs rapides
  ont tourné, le timeout de 600 s de realVerify n'est pas éprouvé sur ce chemin.

## Dette restante

- setDepends n'a aucune sous-commande CLI (le test pose la dépendance par la lib) : impossible de
  corriger un depends_on après création sans réécrire le lot.
- FIA-22 (persister le rapport de /reintegrate --execute) et FIA-19/20/21 (handoff partagé en
  vague, péremption du fleet, écriture outillée du fleet) restent ouverts au catalogue.
