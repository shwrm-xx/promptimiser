## Objectif
Qu'un `/scope` prépare toujours la session fraîche qui lancera les lots en sous-agents au modèle préconisé et consolide dette / à trancher ; `/epicmaster` standalone pour tous les lots ouverts (une epic ou plusieurs), confirmation classée par epic, tout coché, décochable.
## Décisions (et pourquoi)
- Troisième voie d'exécution (sous-agents dans UNE session), distincte de la vague D3 : pas de `fleet join` — la garde de périmètre protège une session, pas ses sous-agents ; le périmètre est transmis dans le brief et le maître commite borné (`git add -- ':(glob)…'`).
- Lot sans périmètre = exclusif (seul en vol), pas « non parallélisable » : un sous-agent sans zone réservée tourne très bien seul.
- Owner `master/lot-N` distinct par lot : seul moyen de garder N lots in_progress (régime fleet de `startLot`) ; conséquence assumée : `costLotFor` n'impute pas le coût quand plusieurs lots sont en vol.
- Borne de budget maître = min(zone rouge résolue, seuil session fraîche 300k) : sur 1M la zone rouge (850k) ne borne rien d'utile ; ~6k tokens/lot côté maître (brief + rapport ≤ 250 mots + clôture), socle 60k — estimations prudentes, jamais mesurées.
- Modèle maître : opus dès qu'un lot le préconise, sinon majoritaire ; effort medium (orchestration, pas de raisonnement sur le code).
- Handoff maître sans brief de lot (régénérable par `--brief`) pour rester sous le cap d'injection de 6000 caractères.
- `/scope` ne démarre plus de lot d'office ; l'ancienne question à 3 choix disparaît (les vagues sont calculées par epicmaster) ; exception sur demande explicite.
