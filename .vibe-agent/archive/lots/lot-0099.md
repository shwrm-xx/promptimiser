# Lot #99 — Fiabilité vague : handoff par lot, purge fleet, écriture outillée

- epic : Archive à tiroirs · clos : 2026-07-27 · commit : 1e0433e · session : courante
- verify : node test/run-tests.js → OK (1576 OK / 0 échec) · coût : non mesuré

## Objectif

Fermer quatre pertes d'état SILENCIEUSES propres aux vagues parallèles (FIA-19 à FIA-22 du
catalogue `mwn/promptimizer-archive-handoffs/02-catalogue-deperditions-fiabilisation.md`), sans
toucher à l'invariant mono-session.

## Décisions (et pourquoi)

- **Handoff par lot en écriture, repli en lecture seulement.** `handoff.md` était clé sur le seul
  root : N filles sur un même checkout s'écrasaient à chaque Stop. Une fille inscrite au fleet
  écrit `handoff-lot-<id>.md`. En lecture elle essaie son fichier puis retombe sur `handoff.md`
  (elle démarre donc sur le handoff de l'orchestrateur tant qu'elle n'a pas écrit le sien) ; en
  écriture, **jamais** de repli — ce serait exactement le last-writer-wins supprimé.
- **Activation restreinte au root partagé** (`lot.worktree` vide). En mode worktree chaque fille a
  déjà son `.vibe-agent` isolé : un fichier par lot y serait mort-né (personne ne le lirait).
- **Le chemin MANUEL devait suivre, sinon régression.** Une fille écrivant un `/close-batch` dans
  `handoff.md` l'aurait vu masqué par son propre handoff auto (lu en premier). `close-batch.js`
  résout donc le chemin (via l'id de session persisté) et l'annonce en tête de checklist. Le cas
  mono-session « deux /close-batch successifs s'écrasent » n'est PAS corrigé : design assumé.
- **`clearWave` plutôt qu'une boucle `removeLot`** : N lectures-écritures = N fenêtres de course
  (cf. en-tête de `lib/fleet.js`). Un seul `saveFleet(lots: [])`. Et jamais de création ex nihilo :
  `existsSync` d'abord, sinon les tests qui injectent un fleet en mémoire créeraient un fichier.
- **Snapshot avant purge → dans le rapport, pas dans l'archive.** Vider `fleet.json` efface la
  composition de la vague (qui tenait quoi, `ext_requests`). Plutôt que d'ouvrir un canal archive
  (pare-feu à respecter), le snapshot part dans le rapport FIA-22 — un artefact qui existait déjà
  au moment où l'information disparaît.
- **`fleet show` lit le fichier AVANT tout `loadFleet`.** `readJson` met un JSON invalide en
  quarantaine dès la première lecture : après un `loadFleet`, on ne saurait plus distinguer
  « absent » de « corrompu » — que `loadFleet` confond de toute façon.
- **`--session` avec repli sur `session-state.json`.** La spec exigeait un refus explicite sans
  propriétaire ; mais l'assistant n'a AUCUN moyen de connaître son propre `session_id`. Repli sur
  l'id persisté, refus explicite si même celui-ci manque.
- **Rapport écrit avant toute sortie du CLI**, pas dans `runPipeline` : c'est le seul point qui
  couvre tous les chemins de retour (conflit, gate rouge, succès) d'un coup. Un refus
  (`nothing-ready`, `no-gate`) n'écrit rien — aucun diagnostic à conserver.
- **`Number(null) === 0`** : le refus `--id` manquant teste la PRÉSENCE du flag avant sa finitude,
  sinon `fleet ready` sans `--id` allait chercher un lot #0 fantôme (bug attrapé par les tests).

## Vérifié

- Deux filles (`s-a`, `s-b`) sur le même repo : chacune écrit et relit SON handoff, `handoff.md`
  reste intact ; une session hors vague lit toujours `handoff.md` (invariant préservé).
- Mode worktree → `handoffFile` renvoie bien `handoff.md`.
- `/close-batch` annonce `handoff-lot-11.md` pour la fille du lot #11.
- Garde PreToolUse : l'ex-fille réintégrée n'est plus refusée hors périmètre, la sœur encore en
  vol l'est toujours (le filtre ne désarme pas la vague).
- `clearWave` idempotent, et ne crée jamais un `fleet.json` absent.
- CLI `fleet` : tous les refus (id absent/non numérique, state invalide, propriétaire introuvable,
  fleet illisible), avertissements (id hors plan, sans périmètre), diagnostic du JSON corrompu
  sans quarantiner le fichier, sous-verbe non pris pour un argument orphelin.
- Rapport écrit MÊME en échec, portant la sortie intégrale du gate rouge et nommant le coupable ;
  deux runs → deux fichiers distincts ; un refus n'en écrit aucun.
- Suite complète : 1576 OK / 0 échec. Build du plugin (`build-plugin.js`) OK.

## Non vérifié

- Aucune vague RÉELLE multi-sessions Claude Code : tout est prouvé en bac à sable (hooks invoqués
  avec des `session_id` distincts sur un même repo git), jamais avec deux vraies sessions
  concurrentes ni avec une course d'écriture simultanée sur `fleet.json`.
- Le canal plugin déployé (`~/.claude/plugins/.../1.6.2`) n'a pas été redéployé : les changements
  ne sont actifs qu'après réinstallation du plugin.

## Dette restante

- `fleet join --session` retombe sur `session-state.json`, fiable seulement après le premier
  SessionStart de la session.
- Pas de `fleet leave` : une fille ne peut pas se désinscrire sans passer par la réintégration.
- `handoff-lot-*.md` orphelins purgés uniquement à la clôture d'une vague : une vague abandonnée
  (jamais réintégrée) laisse ses fichiers sur disque.
- Le rapport de réintégration n'est jamais purgé (`.vibe-agent/logs/` croît sans plafond).
