# Lot #120 — Borne de verify de clôture réglable (fin du faux timeout)

- epic : Preuve de clôture fiable · clos : 2026-07-29 · commit : b11821b
- verify : `node test/run-tests.js` → OK

## Objectif

Réparer la preuve de clôture de ce dépôt : le budget de la verify de clôture (120 s) était passé
sous la durée réelle de la suite (~135 s, 2020 tests), si bien que `/close-batch` rendait
« timeout » sur une suite verte — et que `backlog.js done` sans `--verify-verdict` (lot #119)
aurait persisté `closed_verify: 'timeout'` au lieu de `'ok'` pour tous les lots suivants.

## Décisions (et pourquoi)

- **Les deux pistes, pas l'une ou l'autre** (arbitrage Marwan). Relever seulement le défaut
  laisse le même piège se refermer quand la suite aura encore grossi ; ne rendre que la borne
  réglable laisse tout autre dépôt à suite longue en timeout par défaut, avec un symptôme
  (« timeout » sur suite verte) qui n'oriente vers rien. Défaut relevé **avec marge** (300 s,
  plus du double du mesuré : une marge sur la croissance, pas un ajustement au ras) **et** borne
  posable par projet.
- **`rules.yaml` plutôt qu'une variable d'env de production.** L'env `PMZ_VERIFY_CLOSE_MS` reste
  test-only et n'est PAS un contournement viable : un test verrouille le défaut, donc l'exporter
  casse la suite qu'on cherche à vérifier. `rules.yaml` est déjà la surface de réglage du projet
  (lot #112) ; une deuxième borne n'a donc introduit ni fichier de config ni env nouvelle.
- **Contrat de lecture identique au lot #112** : `lib/rules.js` (lecteur de scalaires, zéro
  dépendance), bornes de plausibilité [1 s, 1 h] traitées comme **absence** de valeur et non
  rabotées, fail-open sur fichier absent/corrompu. Un `verify_close_ms: 500` est une faute de
  frappe, pas une demande de 0,5 s.
- **Le message de timeout nomme la clé à poser.** Le coût réel du bug du #119 n'était pas la
  borne trop courte mais l'absence de piste : un « non terminée dans le délai » qui n'oriente
  vers rien fait chercher dans le code. Même mention sur le verdict `timeout` du CLI `done`.
- **La borne ne couvre que les chemins pilotés par l'assistant.** L'auto-clôture du hook `Stop`
  garde `VERIFY_AUTOCLOSE_MS` (2,5 s), non réglable : un hook ne doit jamais pendre, et le
  lot #111 a déjà tranché qu'un timeout y laisse le lot ouvert.
- **Ce dépôt pose 600 s**, au-delà du défaut : sa suite est passée de ~35 s (lot #90) à ~135 s
  (lot #120) en 30 lots. Le défaut le couvre aujourd'hui ; la borne locale couvre la pente.

## Vérifié

- `node test/run-tests.js` → 2020 OK · 0 échec (23 assertions ajoutées).
- Le câblage config est prouvé **sans override d'env** : une borne courte dans `rules.yaml`
  déclenche la branche timeout de `/close-batch` ET fait persister `closed_verify: 'timeout'`
  par `backlog.js done` — c'est bien `rules.yaml` qui est consulté, pas seulement la lib.
- Bout en bout sur le dépôt réel : `/close-batch` rend « Verify : OK » là où il rendait
  « timeout » avant le lot.
- Build du canal plugin OK (2.1.0), gabarit `rules.yaml` embarqué avec la clé commentée.

## Non vérifié

- Le plugin **installé** (cache 2.1.0) garde l'ancienne borne jusqu'à la prochaine release :
  sur cette machine (canal plugin uniquement), une clôture passant par le plugin installé
  rendra encore « timeout ». La clôture de ce lot a donc été faite avec le script du worktree.
- Aucune mesure de la durée de la suite sur une autre machine / en CI : les ~135 s sont un
  mesuré local (deux runs).

## Dette restante

- Le lot #119 avait déjà noté que `VERIFY_CLOSE_MS` dérivait ; rien ne **surveille** cette
  dérive. Une suite qui franchira 600 s ici reproduira le symptôme, et seul le message de
  timeout l'orientera. Une mesure de la durée de la verify (persistée avec le verdict, comme
  `closed_verify`) permettrait de prévenir avant de subir — candidat à un lot futur.
- `VERIFY_CLOSE_MS` reste exporté (défaut + env, sans `rules.yaml`) : plus aucun appelant de
  production ne l'utilise, seuls les tests le lisent pour verrouiller le défaut.
