réfutée** sur cette étude — voir la réserve méthodologique en fin de document. Trois entrées sont

## Déperditions (narratif/décisions/résultats produits puis perdus)

### DEP-1 [effort M] Archiver le handoff manuel riche avant sa destruction

**Problème** — Le handoff riche de fin de lot (décisions+pourquoi, non-vérifié, dette — template fresh-session.md:29-49) n'a qu'une vie : injecté une fois au SessionStart, markConsumed le rebascule en auto (remplacement du marqueur par writeFileSync), puis le premier Stop suivant l'écrase via writeAutoHandoff. Le fichier est gitignoré (.vibe-agent/.gitignore:9 pattern *) : les handoffs riches des 90 lots clos ont tous disparu sans trace.

**Évidence** — `promptimizer/lib/handoff.js:79-88 (markConsumed) + promptimizer/hooks/session-start.js:65 + promptimizer/hooks/stop.js:219 (writeAutoHandoff à chaque tour)`

**Proposition** — Dans markConsumed (et dans writeAutoHandoff juste avant d'écraser un contenu portant MANUAL_MARKER), copier d'abord le contenu manuel vers .vibe-agent/archive/handoffs/<YYYY-MM-DD>-lot-<N>.md (append-only, un fichier par lot, écriture tmp+rename, try/catch fail-open : l'échec d'archivage n'empêche jamais la consommation). Aucun hook ne lit jamais ce dossier — session-start.js reste inchangé (liste blanche codée en dur, session-start.js:63-68). Whitelister !archive/ et !archive/** dans templates/vibe-gitignore + git add best-effort façon saveBacklog (lib/backlog.js:221-231). Fonctionne à l'identique dans les deux canaux (chemin relatif au projet, pas au package).

**Corrections issues de la vérification adversariale** — 1) Le second point d'interception proposé (« dans writeAutoHandoff juste avant d'écraser un contenu portant MANUAL_MARKER ») est du code mort : writeAutoHandoff refuse déjà d'écraser tout fichier sans AUTO_MARKER (handoff.js:132 « if (fs.existsSync(f) && !raw.includes(AUTO_MARKER)) return false ») — un handoff manuel non consommé n'atteint jamais l'écrasement. Le seul point de destruction est markConsumed (handoff.js:84) ; archiver là uniquement. 2) Le whitelist dans templates/vibe-gitignore ne couvre que les projets FUTURS : bootstrap copie par copyIfAbsent (promptimizer/lib/bootstrap.js:51), les projets déjà initialisés (dont les 90 lots évoqués) gardent l'ancien .gitignore et `git add` refusera un fichier ignoré (cf. commentaire bootstrap.js:118-121). Prévoir soit `git add -f` best-effort, soit un append idempotent de `!archive/` + `!archive/**` dans le .gitignore existant avant staging. 3) « Un fichier par lot » entre en tension avec « append-only » : /fresh-session peut produire plusieurs handoffs manuels dans un même lot/jour ; un nom fixe <date>-lot-<N>.md s'écraserait. Ajouter un suffixe d'unicité (heure ou compteur) ou refuser l'écrasement si le fichier existe. 4) Point de conception à trancher (tier 1 de l'archive à tiroirs) : markConsumed n'a que le contenu brut ; la fiche par lot restera le brut tel quel — acceptable, mais le nommer tier 2 serait plus juste dans le référentiel.

**Vérification (existence du problème)** — Tentative de réfutation échouée — le problème existe. (1) Le handoff manuel riche (décisions, non-vérifié, dette : promptimizer/commands/fresh-session.md:29-49 ; aussi close-batch.md:22-23) est écrit dans l'UNIQUE fichier .vibe-agent/handoff.md (promptimizer/lib/handoff.js:2 « UN fichier…, ÉCRASÉ à chaque tour », handoff.js:25-27). (2) Au SessionStart suivant il est injecté puis immédiatement rebasculé en auto par markConsumed (promptimizer/hooks/session-start.js:63-68 ; promptimizer/lib/handoff.js:79-88 : simple remplacement de marqueur par writeFileSync, aucune copie). (3) Le premier Stop suivant l'écrase intégralement : promptimizer/hooks/stop.js:219 appelle writeAutoHandoff qui réécrit tout le fichier (handoff.js:128-199, writeFileSync ligne 199) — le garde ligne 132 ne protège que tant que le AUTO_MARKER est absent, or markConsumed vient de l'y mettre. (4) Rien n'est versionné : le template promptimizer/templates/vibe-gitignore ignore tout (« * » ligne 7) et ne whiteliste que .gitignore/backlog.json/rules.yaml (lignes 8-10) — handoff.md n'a donc aucune trace git. (5) Aucun mécanisme d'archivage n'existe : git grep -i archiv sur lib/hooks/commands/skills ne remonte que install/package.js (packaging zip, sans rapport). Feature existante couvrant le besoin : aucune.


### DEP-2 [effort S] Persister la checklist de clôture et le non-vérifié

**Problème** — La checklist /close-batch (fait / non fait / non vérifié, verify exécutée, bloc économie de contexte) est émise sur stdout uniquement (process.stdout.write) puis perdue avec le transcript. Le « non vérifié explicitement listé » n'est qu'une consigne discursive (close-batch.md:12, rules.yaml require_unverified_items purement déclaratif) : backlog.json n'a aucun champ unverified, et note (≤200c, écrasée à chaque noteLot) est le seul champ libre par lot.

**Évidence** — `promptimizer/scripts/close-batch.js:96 (stdout seul) + promptimizer/lib/backlog.js:491-496 (noteLot écrase, MAX_NOTE)`

**Proposition** — Étape supplémentaire dans close-batch.md : l'assistant écrit la fiche tier 1 du lot (checklist remplie + non-vérifié + décisions) dans .vibe-agent/archive/handoffs/<date>-lot-<N>.md (même tiroir que l'opportunité 1, même fichier — le handoff riche ET la checklist forment la fiche du lot). Zéro code hook : c'est une consigne de commande .md, donc portée automatiquement par les deux canaux (build-plugin.js copie commands/*.md, réécriture ${CLAUDE_PLUGIN_ROOT} sans script nouveau). Jamais lue au démarrage.

**Corrections issues de la vérification adversariale** — 1) Gitignore/durabilité : le template .vibe-agent/.gitignore ignore tout sauf backlog.json et rules.yaml (promptimizer/templates/vibe-gitignore:7-10) — les fiches archive/ seraient donc NON versionnées (durables sur disque local seulement, perdues au clone). Décider explicitement : soit assumer le local-only, soit whitelister `!archive/` dans le template ; dans ce cas, noter que bootstrap fait copyIfAbsent (lib/bootstrap.js:51) et ne mettra pas à jour les projets déjà bootstrappés — la consigne .md peut demander à l'assistant d'ajouter la ligne si absente. 2) Préciser dans la consigne que l'assistant écrit la checklist REMPLIE (fait/non fait/non vérifié), pas le gabarit « à confirmer » émis par close-batch.js:74-83. 3) Réaffirmer le pare-feu dans la consigne même : archive/ n'est jamais lue/listée pour récupérer du contexte, consultation humaine sur demande uniquement. 4) Définir le comportement si le fichier <date>-lot-<N>.md existe déjà (lot rouvert le même jour) : append ou suffixe, pour éviter l'écrasement silencieux d'une fiche.

**Vérification (existence du problème)** — Thèse confirmée sur pièces. (1) La checklist de clôture est émise sur stdout uniquement : promptimizer/scripts/close-batch.js:96 (`process.stdout.write(out)`), avec « Non vérifié explicitement listé : à confirmer » en simple ligne de checklist (close-batch.js:83) — aucun writeFileSync dans ce script, rien n'est persisté. (2) Le « non vérifié » n'est qu'une consigne discursive : promptimizer/commands/close-batch.md:12 (« Mapper chaque point demandé vers fait / non fait / non vérifié ») et promptimizer/templates/rules.yaml:35 (`require_unverified_items: true`) — ce flag n'est lu par AUCUN code (git grep « require_unverified » ne renvoie que le template lui-même). (3) Le schéma de lot dans backlog.json n'a aucun champ `unverified` (normalisation complète du lot : promptimizer/lib/backlog.js:170-205 — id/title/scope/status/model_hint/…/note, rien d'autre en champ libre) ; `note` est bien le seul champ libre, plafonné à 200 caractères (MAX_NOTE : backlog.js:61) et écrasé à chaque appel de noteLot (backlog.js:491-497, `lot.note = trunc(note, MAX_NOTE)` ligne 495). (4) Aucun mécanisme d'archive n'existe : git grep « archive|handoffs » ne trouve que le packaging zip d'install (install/package.js), pas de .vibe-agent/archive. Le seul réceptacle du handoff riche est .vibe-agent/handoff.md, UN fichier ÉCRASÉ à chaque tour (promptimizer/lib/handoff.js:2) et plafonné à 6000 caractères à l'injection (handoff.js:19) — donc même quand l'assistant y met le non-vérifié (close-batch.md étape 6), l'info est détruite au lot suivant.


### DEP-3 [effort S] Persister le résultat du verify d'auto-clôture dans le lot

**Problème** — À l'auto-clôture, runVerify est exécuté mais son verdict ne sert qu'à un systemMessage éphémère (closureProofMessage) : doneLot ne persiste que closed_commit/closed_at/closed_session_id/closed_occupancy/lot_number. Un lot clos sur verify en ÉCHEC est stocké 'done' à l'identique d'un lot prouvé (test/run-tests.js:3691-3692 le confirme) — « clos sans preuve » est irrécupérable a posteriori.

**Évidence** — `promptimizer/hooks/stop.js:204-211 (verdict jeté après message) + promptimizer/lib/backlog.js:405-410 (aucun champ de résultat verify)`

**Proposition** — Ajouter un champ closed_verify ('ok'|'fail'|'timeout'|'none') posé par stop.js après le runVerify existant (patch du lot via une petite fonction backlog type setClosedVerify, saveBacklog atomique déjà en place, try/catch fail-open — la clôture reste acquise même si l'écriture échoue). Exposer la colonne dans l'export CSV/MD existant (EXPORT_COLUMNS). Pur stdlib, aucun changement d'injection.

**Corrections issues de la vérification adversariale** — 1) Sémantique à documenter : distinguer champ ABSENT (lot legacy, clôture manuelle CLI, ou écriture échouée/watchdog tué pendant le verify) de 'none' (lot sans commande verify) — sinon 'none' devient ambigu. 2) Le setter (setClosedVerify) doit être défensif : n'agir que sur un lot status==='done' et ne jamais écraser une valeur déjà posée (idempotence, cohérent avec doneLot backlog.js:404). 3) Mapping verdict depuis runVerify : ok→'ok', ok:false+timedOut→'timeout', ok:false→'fail' (project.js:163-165) ; envisager de persister aussi le tail (5 dernières lignes) pour le diagnostic a posteriori — optionnel, hors périmètre minimal. 4) Mettre à jour le test e2e T4 (test/run-tests.js:3691-3692) pour asserter closed_verify==='fail', et ajouter un cas 'ok'/'none'. 5) Hors périmètre minimal mais à noter : la clôture manuelle via scripts/close-batch.js (qui partage runVerify, project.js:155) ne poserait pas le champ — soit l'y ajouter aussi, soit assumer champ absent = clôture manuelle.

**Vérification (existence du problème)** — Réfutation tentée, échec : le problème existe. (1) promptimizer/hooks/stop.js:204-212 — à l'auto-clôture, runVerify est exécuté APRÈS doneLot et son verdict ne sert qu'à construire closureProofMessage poussé dans `parts` (systemMessage éphémère, stop.js:210-211, 224-225) ; aucune écriture backlog dans ce bloc. (2) promptimizer/lib/backlog.js:400-422 (doneLot) — champs persistés : status, closed_commit (406), closed_at (407), closed_session_id (408), closed_occupancy (409), lot_number (410), integrations RTK (414-421) ; aucun champ de verdict verify. (3) `git grep closed_verify` → zéro occurrence dans tout le dépôt : aucune feature existante ne couvre le point. (4) EXPORT_COLUMNS (promptimizer/lib/backlog.js:738) contient `verify` (la COMMANDE, pas le verdict) — l'export ne distingue donc pas un lot prouvé d'un lot clos sur échec. (5) test/run-tests.js:3691-3692 confirme le comportement : verify en ÉCHEC → message visible mais lot stocké status='done' à l'identique, rien de distinctif persisté. L'évidence citée est exacte.


### DEP-4 [effort S] Écriture atomique de handoff.md (tmp+rename)

**Problème** — handoff.md est le seul artefact écrit en fs.writeFileSync direct (writeAutoHandoff:199 et markConsumed:84) alors que fsjson.writeAtomic (tmp unique pid+timestamp puis rename) existe et protège ledgers/backlog/fleet. Un crash mi-écriture laisse soit un fichier tronqué avec AUTO_MARKER (injecté amputé), soit un fichier sans marqueur : readHandoff:68 renvoie alors null ET writeAutoHandoff:132 refuse toute réécriture (traité comme notes utilisateur) — canal handoff mort silencieusement et définitivement, dernier état connu perdu à chaque session suivante.

**Évidence** — `promptimizer/lib/handoff.js:199 et :84 vs promptimizer/lib/fsjson.js:7-16`

**Proposition** — Factoriser une variante texte de writeAtomic dans fsjson.js (writeAtomicText(file, str), même motif tmp pid+timestamp+rename, return false en échec) et l'utiliser dans writeAutoHandoff et markConsumed. Cross-platform (renameSync), zéro dépendance, fail-open inchangé. Ajouter au passage un test writeAtomic dans run-tests.js (aucune occurrence aujourd'hui).

**Corrections issues de la vérification adversariale** — Deux nuances mineures : (1) le scénario « fichier tronqué sans marqueur » est légèrement surévalué pour writeAutoHandoff — AUTO_MARKER est la PREMIÈRE ligne écrite (handoff.js:143), donc une troncature partielle conserve généralement le marqueur ; le cas « canal mort définitivement » exige une troncature dans les tout premiers octets ou un fichier vide. Il reste réel pour markConsumed (handoff.js:84) où la position de MANUAL_MARKER dépend du template manuel rédigé par l'assistant, et une troncature avec marqueur présent produit quand même un handoff amputé injecté (lignes pmz:skip/pmz:summary coupées). (2) Dans writeAutoHandoff, retourner le résultat de writeAtomicText (au lieu du `return true` inconditionnel actuel ligne 200) pour que l'appelant sache si l'écriture a réellement abouti. Sinon la proposition est viable telle quelle, y compris le test writeAtomic à ajouter dans test/run-tests.js.

**Vérification (existence du problème)** — Vérifié dans le code actuel : (1) promptimizer/lib/handoff.js:199 (writeAutoHandoff) et :84 (markConsumed) écrivent handoff.md en fs.writeFileSync direct, sans tmp+rename ; (2) fsjson.writeAtomic (tmp unique pid+timestamp puis renameSync, return false en échec) existe bien à promptimizer/lib/fsjson.js:7-16 et protège ledgers (ledger.js:123-124,197), backlog (backlog.js:230,596), fleet (fleet.js:152), etc. ; (3) le scénario de mort du canal est réel : writeFileSync ouvre en 'w' (troncature immédiate) — un crash/kill du hook (stop.js tourne à chaque fin de tour) entre troncature et écriture laisse un fichier vide ou partiel ; s'il ne contient pas AUTO_MARKER, readHandoff renvoie null (handoff.js:68) ET writeAutoHandoff refuse toute réécriture (handoff.js:132 : existsSync + !includes(AUTO_MARKER) → return false), le tout fail-silent ; (4) aucun test writeAtomic dans test/run-tests.js (grep « writeAtomic » : 0 occurrence, seules les sections handoff K1-K4 existent, run-tests.js:910-962) ; (5) le motif tmp+rename texte est déjà dupliqué inline dans lot.js:42-44 (writeEpic) et trigram.js:47, ce qui appuie la factorisation writeAtomicText proposée.


### DEP-5 [effort S] Quarantaine des ledgers JSON corrompus au lieu du reset muet

**Problème** — readJson renvoie le fallback en silence sur JSON invalide, puis le premier recordRead/recordModify réécrit atomiquement un ledger neuf : tout l'accumulé trans-session (summaries, waste_by_file, avoid_reread_notes) est détruit définitivement, sans signal ni copie — alors que le fichier illisible était encore sur disque juste avant la réécriture.

**Évidence** — `promptimizer/lib/fsjson.js:19-26 (fallback silencieux) + promptimizer/lib/ledger.js:145 et :154 (writeAtomic écrase au tour suivant)`

**Proposition** — Dans readJson, sur JSON.parse en échec avec fichier EXISTANT non vide : renommer best-effort le fichier en <nom>.corrupt (renameSync dans le try, un seul exemplaire — écraser l'ancien .corrupt) avant de renvoyer le fallback. Le contenu reste consultable à la main (tiroir brut), jamais relu par les hooks (les lecteurs ciblent le nom exact), ignoré par la whitelist gitignore. Aucun changement d'API, fail-open préservé (tout dans le try existant).

**Corrections issues de la vérification adversariale** — 1) Restructurer readJson pour distinguer échec de LECTURE (ENOENT → fallback direct, pas de rename) et échec de PARSE (fichier lu non vide → quarantaine) : lire d'abord le contenu, puis parser dans un try imbriqué ; le rename lui-même dans son propre try best-effort (course entre deux hooks concurrents : le second rename échoue ENOENT, inoffensif). 2) Décider consciemment le cas fsjson.js:22 (JSON valide mais non-objet, ex. un nombre) : il renvoie aussi le fallback et sera écrasé sans quarantaine — soit le quarantainer aussi, soit le documenter comme exclu. 3) Noter que la quarantaine s'applique à TOUS les consommateurs de fsjson (advisory, backlog, fleet, gitdebt, loopwatch, lot, rtk-metrics, rtk-status, turnstats), y compris les fichiers d'état hors-projet sous ~/.claude, pas seulement les ledgers — souhaitable mais à assumer dans la doc. 4) Cas backlog.json (fichier VERSIONNÉ, whitelisté vibe-gitignore:9) : après quarantaine, git verra backlog.json supprimé jusqu'à sa réécriture — comportement acceptable (git garde l'historique) mais à mentionner. 5) Ajouter un cas dans test/run-tests.js (JSON corrompu → .corrupt créé + fallback renvoyé + jamais d'exception).

**Vérification (existence du problème)** — Réfutation tentée, échec : le problème existe. (1) promptimizer/lib/fsjson.js:19-26 — readJson attrape toute erreur (dont JSON.parse invalide) et renvoie le fallback en silence, aucune copie ni signal ; git grep "corrupt" ne montre AUCUNE quarantaine dans lib/ (seul merge-settings.js:132-147 signale la corruption, mais uniquement pour le sidecar settings, pas les ledgers). (2) promptimizer/lib/ledger.js:47 et :55 — loadReadLedger/loadContextLedger repartent d'un objet vide sur fallback null, détruisant summaries/avoid_reread_notes (rl) et waste_by_file/waste_bucket/estimated_context_waste (cl), accumulés trans-session (waste_bucket est explicitement « trans-session, monotone croissant », ledger.js:64-66). (3) La réécriture destructrice est réelle : recordRead écrit aux ledger.js:123-124, recordOccupancy à :145, recordModify à :154 — writeAtomic (fsjson.js:7-16) rename par-dessus le fichier corrompu encore présent. (4) Aucune feature existante ne couvre : le seul test de corruption de ledger (test/run-tests.js:2164-2173) vérifie uniquement silence + exit 0, pas la préservation. (5) Les deux ledgers sont gitignorés (template vibe-gitignore : « * » puis whitelist !backlog.json/!rules.yaml) — donc pas de récupération via git, et un fichier .corrupt serait bien ignoré comme le propose la fiche.


### DEP-6 [effort S] closed_session_id et closed_occupancy vides sur clôture CLI

**Problème** — La commande CLI `done` appelle doneLot(root, id, flag('commit')) sans sessionId ni occupancy — or c'est le chemin recommandé par /close-batch. Mesuré sur le backlog réel : closed_session_id présent sur 1/90 lots done, closed_occupancy sur 0/90 : l'attribution session et la métrologie d'occupation à la clôture sont perdues sur quasi tout l'historique.

**Évidence** — `promptimizer/scripts/backlog.js:326-327 vs promptimizer/lib/backlog.js:400-410 (paramètres prévus mais jamais fournis)`

**Proposition** — Accepter des flags optionnels --session et --occupancy sur `backlog.js done`, et faire renseigner --session par la commande close-batch.md (le session_id est connu de l'assistant via le contexte hook/statusline). À défaut de flag, comportement inchangé (null). Pur CLI stdlib, aucun hook touché, compatible plugin (chemins déjà réécrits en ${CLAUDE_PLUGIN_ROOT}).

**Corrections issues de la vérification adversariale** — 1) Ne pas compter sur l'assistant pour taper --session : le CLI doit pouvoir s'auto-remplir depuis .vibe-agent/session-state.json via rawSessionId (promptimizer/lib/state.js:53-62), qui contient bien le session_id de la session courante (posé par user-prompt-submit/stop au tour même) — p.ex. `--session auto` ou auto-fill par défaut avec opt-out. Un id tapé à la main risque d'être halluciné et de fausser la vérification de suggestedTitle (lib/backlog.js:394-396). 2) Idem pour --occupancy : l'assistant ne connaît pas occ de façon fiable ; le CLI peut lire le dernier occ miroité au ledger par recordOccupancy (promptimizer/hooks/stop.js:108) ; si flag manuel conservé, coercer en Number() car doneLot exige Number.isFinite (lib/backlog.js:409) et un argv est une string. 3) Mettre à jour les commentaires devenus faux (« Absent pour une clôture manuelle via le CLI », lib/backlog.js:396 et 399) et la ligne de contrat correspondante d'ARCHITECTURE.md — doc anti-péremption. 4) Couvrir dans test/run-tests.js (le CLAUDE.md projet impose les tests avant tout commit touchant lib/ ou scripts/).

**Vérification (existence du problème)** — Confirmé sur le code ET empiriquement. ### AM-3 [effort M] Lier l'état de tour au transcript, pas au seul session_id

**Problème** — La clé d'état est sha1(session_id) seule (occupancy.js:192) : aucun composant projet ni transcript. Le turns.json stocke un offset d'octets DANS le transcript (turnstats.js:167-168) sans mémoriser QUEL transcript : si le même session_id est réutilisé avec un autre fichier (session reprise/téléportée dans un autre cwd, transcript remplacé), la seule garde est prevOffset > size (turnstats.js:109-112) — un nouveau transcript PLUS GROS que l'offset stocké passe silencieusement la garde et scanRange mesure alors un faux « tour » chevauchant deux fichiers (deltas, busts et hitRate fantaisistes, injectés dans le FIFO qui nourrit evaluateDrift). Les paliers d'occupation (occupancy.js:290-306) et gitdebt (head/turns, gitdebt.js:64-69) sont pareillement partagés entre les deux contextes : paliers déjà « franchis » dans le projet A muselant les alertes dans le projet B.

**Évidence** — `promptimizer/lib/occupancy.js:186-194 ; promptimizer/lib/turnstats.js:106-115,167-173`

**Proposition** — Persister le transcript_path (ou son sha1) dans turns.json à chaque écriture et, dans computeTurn, traiter un path différent comme baselineReset (même branche que prevOffset > size, turnstats.js:109-112) — correction locale, aucun changement de format de clé, rétrocompatible (champ absent = comportement actuel). Optionnellement, pour les états à sémantique par-projet (bucket, gitdebt), saler stateFileFor avec un 2e composant optionnel (hash du root projet) fourni par les appelants qui le connaissent — signature étendue, défaut inchangé, donc zéro migration. Fail-open intégral, stdlib, identique sur les deux canaux.

**Corrections issues de la vérification adversariale** — 1) Stocker de préférence sha1(transcript_path) plutôt que le path brut, ou comparer après normalisation (casse/séparateurs Windows), pour une comparaison stable cross-platform et un turns.json compact. 2) Mettre à jour le commentaire d'occupancy.js:299-300 (« un vrai reset = nouvelle session_id => nouveau fichier d'état ») dont l'hypothèse devient partiellement fausse si on salue les états par projet. 3) Pour le salage optionnel de stateFileFor : TOUS les appelants d'une même famille d'état doivent passer le même sel (ex. resyncBucket occupancy.js:238-246 et evaluate occupancy.js:290 depuis stop.js), sinon désynchronisation palier/resync — à traiter comme un lot séparé si retenu, la correction principale (transcript_path dans turns.json) suffit au problème décrit. 4) Prévoir le cas transcript_path absent du payload hook (champ manquant → ne jamais déclencher baselineReset, comportement actuel conservé).

**Vérification (existence du problème)** — Faits vérifiés : clé d'état sha1(session_id) seul sans composant projet/transcript (promptimizer/lib/occupancy.js:192) ; turns.json persiste un offset d'octets sans identité du transcript (promptimizer/lib/turnstats.js:167-173) ; seule garde de péremption = prevOffset > size (turnstats.js:109-112), dont le commentaire ligne 110 anticipe explicitement le cas « nouveau fichier » sans le couvrir au-delà du test de taille — un transcript remplacé PLUS GROS que l'offset stocké passe la branche else (turnstats.js:113-114) et scanRange (turnstats.js:118) mesure un faux tour chevauchant deux fichiers, injecté dans le FIFO (turnstats.js:165-166) consommé par evaluateDrift (turnstats.js:197). Aggravation confirmée : sur baselineReset le delta est null (turnstats.js:128,147) donc alerts.resync=false (turnstats.js:161) → resyncBucket jamais déclenché → palier d'occupation monotone périmé qui muselle les alertes (occupancy.js:290-306, jamais redescendu sauf resync). Aucune feature existante ne persiste le transcript_path dans l'état (git grep transcript sur lib/ + hooks/stop.js : néant). Réfutation du déclencheur tentée et échouée : sid réutilisé avec un autre fichier est plausible (session téléportée/rematérialisée, transcript réécrit plus gros) et le code l'anticipe lui-même.


### AM-4 [effort M] État de session multi-écrivains : fin du ping-pong de resets intra-root

**Problème** — session-state.json est un fichier UNIQUE keyé par UN session_id (promptimizer/lib/state.js:24-26) avec reset intégral dès qu'un session_id différent se présente (state.js:40-42). Quand deux sessions tournent sur le même root (chef + fille de vague hors worktree, ou deux fenêtres), chaque hook Stop (promptimizer/hooks/stop.js:118 + saves :132/:171/:175) et UserPromptSubmit (promptimizer/hooks/user-prompt-submit.js:63/:136) d'une session écrase l'état de l'autre : prompt_reminders remis à zéro à chaque alternance (nudges broad/model/occ dupliqués), closure_reminded_for_batch ne tient jamais (rappel de clôture répété chaque tour), et pending_title_rename posé par session-start.js:157 est effacé avant le 2e rappel de user-prompt-submit.js:72-75 (rename perdu).

**Évidence** — `promptimizer/lib/state.js:40`

**Proposition** — Restructurer session-state.json en map { sessions: { <sid>: {flags…} }, last_session_id } : loadSessionState(root, sid) renvoie l'entrée du sid demandé (créée à DEFAULT_STATE si absente, plus jamais de reset croisé), saveSessionState réécrit seulement cette entrée + last_session_id, avec GC des entrées les plus anciennes (cap ~5, champ updated_at par entrée). previousSessionId (state.js:58, consommé par lib/lot.js:suggestedTitle) lit last_session_id — sémantique « dernière session active » préservée. Rétro-compat : un fichier ancien format (session_id à la racine) est migré à la volée en une entrée. Stdlib uniquement, writeAtomic conservé, fail-open inchangé (JSON invalide → map vide) — compatible les deux canaux (aucun nouveau fichier déployé).

**Corrections issues de la vérification adversariale** — 1) Mettre à jour templates/session-state.json au nouveau format (copié par lib/bootstrap.js:56) et les tests qui lisent/valident le fichier brut (test/run-tests.js:1031-1033, :1839, :3493) — la migration à la volée ne couvre pas le template neuf. 2) Documenter la course résiduelle : le read-modify-write du fichier entier entre deux hooks concurrents peut encore perdre la mise à jour de l'entrée de l'autre sid (writeAtomic protège de la corruption, pas du lost-update) — acceptable car flags anti-spam uniquement (pire cas : un rappel dupliqué), mais à acter dans ARCHITECTURE.md ; option de mitigation légère : relire le fichier juste avant écriture et ne fusionner que sa propre entrée. 3) Noter que last_session_id sous deux sessions concurrentes alterne (suggestedTitle peut attribuer à la session sœur) — comportement identique à l'actuel last-writer-wins, pas une régression, mais à mentionner dans le commentaire de previousSessionId.

**Vérification (existence du problème)** — Toutes les évidences sont exactes dans le code actuel. (1) Fichier unique keyé par UN session_id : promptimizer/lib/state.js:24-26 (un seul session-state.json par root) et DEFAULT_STATE à session_id unique (state.js:9-22). (2) Reset intégral dès qu'un session_id différent se présente : state.js:40-42 (`if (sessionId && st.session_id && st.session_id !== sessionId) return Object.assign({}, DEFAULT_STATE, ...)`). (3) Écrivains multiples réels : stop.js:118 (load) + saves :132/:171/:175 ; user-prompt-submit.js:63 (load) + :136 (save INCONDITIONNEL à chaque prompt — l'alternance de deux sessions actives sur le même root garantit donc le ping-pong). (4) Symptômes vérifiés : prompt_reminders remis à zéro à chaque alternance → nudges broad/model/occ redéclenchés (user-prompt-submit.js:92-94, :111, :127-128) ; closure_reminded_for_batch ne tient pas entre deux Stop alternés (stop.js:156-171) ; pending_title_rename posé par session-start.js:157 (sauvé :162) est effacé par le save d'une autre session avant le 2e rappel de user-prompt-submit.js:72-75. (5) Le scénario multi-sessions même root est ANTICIPÉ par le projet lui-même : fleet.js:14-18 documente « N sessions écrivent le même fichier » pour fleet.json, et parallelize.md:7 ne lance rien (les worktrees ne sont que suggérés — rien n'impose qu'une fille tourne hors du root). (6) Aucune feature existante ne couvre : pas de map par sid dans session-state.json (git grep last_session_id → néant) ; le keying par session existe ailleurs (occupancy.js:186-192, fichiers d'état hashés par sessionId en tmpdir) mais PAS pour session-state.json, ce qui confirme le trou.


### AM-5 [effort S] Corréler le snapshot todos au session_id avant injection dans le handoff auto

**Problème** — writeTodoSnapshot persiste le session_id de la session qui a écrit les todos (promptimizer/lib/backlog.js:596-599, écrit à chaque TodoWrite par promptimizer/hooks/post-tool-use.js:47-50), mais writeAutoHandoff est appelé sans session_id (promptimizer/hooks/stop.js:219, promptimizer/hooks/pre-compact.js:28) et handoff.js injecte snap.todos sans aucune corrélation (promptimizer/lib/handoff.js:183-190). Avec deux sessions sur le même root, le Stop de la session A embarque les todos de la session B dans le handoff — la session fraîche suivante reprend les « Tâches en cours » du MAUVAIS fil de travail, déperdition silencieuse du vrai état de A.

**Évidence** — `promptimizer/lib/handoff.js:183`

**Proposition** — Passer input.session_id à writeAutoHandoff(root, sid) depuis stop.js:219 et pre-compact.js:28 ; dans handoff.js, si snap.session_id existe ET diffère du sid écrivain, soit omettre le bloc « Tâches en cours », soit le préfixer d'une mention explicite « (todos d'une autre session : <sid tronqué>) » — jamais d'injection muette de todos étrangers. sid absent (appel legacy/CLI) → comportement actuel conservé (fail-open). Changement local à 3 fichiers, zéro nouveau fichier, aucun impact canaux install/plugin.

**Corrections issues de la vérification adversariale** — 1) Préférer l'annotation à l'omission : omettre le bloc « Tâches en cours » quand les sids diffèrent crée une nouvelle déperdition (les todos de B restent le dernier état connu du root et peuvent être pertinents) ; le préfixe explicite « todos d'une autre session : <sid tronqué à 8 car.> » préserve l'information tout en levant l'ambiguïté. 2) snap.session_id null (snapshot legacy antérieur au champ, ou TodoWrite sans sid) doit être traité comme « pas de corrélation possible » → comportement actuel, jamais comme « session différente ». 3) Garder writeAutoHandoff(root, sid) avec sid optionnel (2e paramètre) pour ne casser aucun appel existant ni les tests (test/run-tests.js à relancer). 4) Dans pre-compact.js le sid est celui de la MÊME session qui compacte — la corrélation y sera quasi toujours positive, c'est le cas Stop multi-sessions qui porte la valeur.

**Vérification (existence du problème)** — Tous les faits cités sont exacts dans le code actuel. (1) Le snapshot todos persiste bien le session_id de l'écrivain : promptimizer/lib/backlog.js:596-599 (`session_id: sessionId || null`), alimenté à chaque TodoWrite par promptimizer/hooks/post-tool-use.js:47-50 (`writeTodoSnapshot(root, ..., input.session_id || null)`). (2) writeAutoHandoff ne reçoit AUCUN session_id : signature `function writeAutoHandoff(root)` à promptimizer/lib/handoff.js:128, appels `writeAutoHandoff(root)` à promptimizer/hooks/stop.js:219 et promptimizer/hooks/pre-compact.js:28. (3) L'injection est bien non corrélée : promptimizer/lib/handoff.js:183-190 lit `readTodoSnapshot(root)` et injecte `snap.todos` sans jamais consulter `snap.session_id` (readTodoSnapshot, backlog.js:606-610, renvoie le raw avec session_id mais handoff.js l'ignore). Tentative de réfutation par couverture existante : rien ne l'empêche — le mécanisme fleet/vagues isole par worktree (roots distincts) donc ne couvre pas deux sessions plates sur le même root ; le fichier snapshot est unique par root, dernier-écrivain-gagne (backlog.js:584-587 « un seul fichier écrasé intégralement ») ; l'état par session (lib/state.js) est keyé par sha1(session_id) mais le snapshot todos ne l'est pas. Pire : le commentaire promptimizer/lib/fleet.js:271-274 confirme que les sous-agents (Task/Agent) écrivent avec un AUTRE session_id — donc même en mono-session, un TodoWrite de sous-agent écrase le snapshot avec un session_id étranger et ses todos sont injectés au Stop comme « Tâches en cours ». Le problème existe réellement.


### AM-6 [effort S] Vague hors worktree : documenter le worktree comme prérequis et détecter le partage de root

**Problème** — Le lancement des sessions filles de vague est manuel et rien n'impose ni ne recommande un worktree (promptimizer/commands/parallelize.md:25-30 ; parallelize.md:7 et ARCHITECTURE.md:420 précisent que rien n'est lancé, « ni branche, ni worktree ») ; le champ worktree de fleet est purement déclaratif (promptimizer/lib/fleet.js:106). **Évidence** — `promptimizer/commands/parallelize.md:25`

**Proposition** — Deux volets sans rien lancer automatiquement : (1) doc — ajouter à l'étape 3 de parallelize.md la consigne de démarrer chaque fille dans un git worktree dédié (git worktree add <dir> <branche suggérée par waveBranch>) et de renseigner le champ worktree de son entrée fleet, en expliquant que .vibe-agent est par-arbre ; (2) détection passive — au SessionStart d'une session inscrite au fleet (fleetLines, promptimizer/hooks/session-start.js:116), si son entrée fleet n'a pas de worktree ET que le root porte déjà un session-state.json d'une autre session récente, émettre un systemMessage one-shot recommandant le worktree. Lecture seule + message, fail-open trivial, aucun nouveau fichier — compatible les deux canaux.

**Corrections issues de la vérification adversariale** — 1) Le critère « session-state.json d'une autre session récente » est trivialement vrai à CHAQUE démarrage (le fichier mono-slot porte toujours le session_id de la session précédente, state.js:40-42) : il faut le raffiner en proxy de concurrence — mtime du fichier sous une fenêtre courte (quelques minutes) via fs.stat ; les faux positifs restent bénins (message consultatif one-shot) mais doivent être assumés dans la doc du hook. 2) Ordre d'exécution : la lecture du session_id précédent doit passer par previousSessionId (state.js:58, lecture brute sans reset) et se faire AVANT loadSessionState/saveSessionState de session-start.js:143/162, qui écrasent le fichier avec l'id de la session courante. 3) Anti-spam : ne pas persister le flag one-shot dans session-state.json (c'est précisément le fichier corrompu par le partage de root) — soit accepter la ré-émission à chaque vrai startup (déjà rare), soit tracer sur l'entrée fleet du lot. 4) Sortie : session-start.js n'émet qu'un write par run ; le plus simple est d'ajouter la ligne d'avertissement au contexte injecté existant (chemin withFleet, session-start.js:82-89) plutôt qu'un systemMessage séparé — sinon vérifier que le double write (injectContext + systemMessage) est accepté par le hook runner.

**Vérification (existence du problème)** — Toutes les affirmations vérifiées. (1) Lancement manuel sans consigne worktree : promptimizer/commands/parallelize.md:25-30 dit « NE RIEN LANCER … le lancement des sessions filles reste manuel » et ne mentionne le worktree qu'en négatif (parallelize.md:7 « aucune branche, aucun worktree ») ; idem ARCHITECTURE.md:420-421. Aucune consigne « git worktree add » nulle part (git grep worktree → seulement parallelize.md:7, fleet.js:106, fleet.js:276). (2) Champ worktree purement déclaratif : promptimizer/lib/fleet.js:106 (trunc + stockage, aucune validation d'existence), utilisé uniquement en affichage (fleet.js:276). (3) Seul fleet.json est conçu pour N écrivains : commentaire explicite fleet.js:13-18 (« N sessions écrivent le même fichier … mutations PAR LOT »). (4) session-state.json est mono-écrivain par conception : promptimizer/lib/state.js:39-42 — dès qu'un session_id différent est vu, loadSessionState remet TOUS les flags à zéro ; deux sessions dans le même root se réinitialisent mutuellement à chaque hook (anti-spam re-déclenchés, pending_title_rename perdu, previousSessionId (state.js:53-66) brouillé). (5) todo-snapshot.json est un fichier unique écrasé intégralement au dernier TodoWrite, quel que soit l'écrivain : promptimizer/lib/backlog.js:584-600 (« un seul fichier écrasé intégralement ») ; readTodoSnapshot (backlog.js:606-609) ne filtre pas par session_id, et ses consommateurs injectent donc potentiellement les todos de l'AUTRE session : handoff (promptimizer/lib/handoff.js:183-190) et resume post-compaction (promptimizer/hooks/session-start.js:107-111). (6) Aucune détection ni avertissement de root partagé n'existe : session-start.js:116 appelle fleetLines mais rien ne compare worktree/session-state ; git grep ne trouve aucun mécanisme de signal. La chaîne handoff est bien dégradée en configuration root partagé, sans aucun garde-fou existant.
